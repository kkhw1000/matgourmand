# Backend 작업 규칙

백엔드 작업을 시작하기 전에 이 문서를 먼저 확인합니다.

## 핵심 규칙

1. 엔티티 생성은 팩토리 패턴을 이용합니다.
2. setter는 지양하되, 부득이한 경우 `setXX` 형태보다는 실제 의미가 드러나는 메소드명으로 작성합니다.

## 권장 규칙

1. 엔티티에는 생성과 상태 변경에 필요한 비즈니스 메소드만 두고, 단순 데이터 변경용 public setter는 만들지 않습니다.
2. Controller는 요청과 응답 처리에 집중하고, 비즈니스 로직은 Service로 분리합니다.
3. API 입출력은 엔티티를 직접 노출하지 말고 Request DTO, Response DTO로 분리합니다.
4. 연관관계는 처음부터 과하게 양방향으로 열지 말고, 필요한 경우에만 추가합니다.
5. enum으로 관리할 수 있는 상태값은 문자열 상수 대신 enum을 우선 사용합니다.
6. 생성일시, 수정일시 같은 공통 컬럼은 가능한 한 일관된 방식으로 관리합니다.
7. 예외는 단순히 던지는 데서 끝내지 말고, 도메인에 맞는 메시지와 응답 형태를 고려합니다.
8. 테스트는 최소한 Service 또는 Repository 단위에서 핵심 흐름이 깨지지 않는지 확인할 수 있게 작성합니다.
9. 엔티티에 `@Builder`를 무분별하게 사용하지 않습니다. 생성 규칙이 중요한 엔티티는 팩토리 메소드나 의도가 드러나는 생성 방식으로 관리합니다.
10. 한 메소드는 가능하면 한 유스케이스에 집중합니다. 예를 들어 `updateStoreInfo`, `changeStoreStatus`처럼 변경 의도가 드러나는 형태를 우선합니다.

## 도메인 간 참조 원칙

1. 타 도메인의 비즈니스 규칙, 정책, 검증이 필요하면 해당 도메인의 Service 또는 도메인 로직을 우선 사용합니다.
2. 타 도메인의 단순 조회나 존재 여부 확인처럼 읽기 전용 정보만 필요하면 Repository 직접 접근도 허용합니다.
3. 단순 속성 조회가 반복되거나 복잡해지기 시작하면 전용 조회 서비스 또는 도메인 서비스 분리를 검토합니다.
4. 타 도메인의 DTO를 그대로 재사용하기보다는 현재 유스케이스에 맞는 DTO나 값만 사용하는 방향을 우선합니다.

## 현재 우선순위

초기 구현은 아래 순서를 기준으로 진행합니다.

1. `User`
2. `Store`
3. `BusinessHour`
4. `Reservation`
